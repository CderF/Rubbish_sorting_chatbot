## 1. STAGE 04 が扱う問題:「ナレッジは変わる」

STAGE 02/03 はナレッジが静的である前提(サイトを一度取得して DB を作り、それに基づいて回答する)。
STAGE 04 はその前提が崩れるケースを扱う。サブ要件は 3 つ。

### 4-1 新ナレッジを取り込むと、回答に反映される

- **場面**: 採点中に、採点側から新しいナレッジファイルが配布される。形式は未確定(**メンター/Slack で要確認** — markdown / CSV / JSON / PDF のいずれか)。内容は「ある品物の分別変更」または「品物の追加」など。
- **「取り込む」= ingest 処理**: ファイルを解析 → 既存ナレッジと同じ構造のレコードに変換 → 構造化 DB / ベクトルストアに書き込み → インデックス再構築。
- **「回答に反映」**: 次の質問で検索がその新レコードにヒットし、LLM がそれを使って回答する。
- **周が作るもの**:
  - ingest コマンド/関数: `ingest(file) → 追加レコード数`
  - ナレッジソース一覧(manifest): 各ファイルの id / 種別 / 取込日時 / hash
  - STAGE 02 の検索層が「基礎クロールデータ + 追加取込データ」の和集合を見るようにする
- **STAGE 02 に依存**: ナレッジレコードのスキーマ、書き込み口、インデックス再構築の方法

### 4-2 旧根拠と新お知らせが併存する場合、断定せず「いつから・何が・どう変わるか」を示す

- **場面**: 早見表に「〇〇 は家庭ごみ」、しかし新お知らせに「2026-04-01 から 〇〇 は資源化ごみに変更」。
- 旧だけ・新だけの回答は不可。「現在(〜3/31)は家庭ごみ、4/1 以降は資源化ごみ、切替日 2026-04-01。出典: 早見表 URL + お知らせ URL」と答える。
- **必要な仕組み**:
  - 各レコードに `effective_date`(適用開始)、`published_at`(公示日)、任意で `valid_until`
  - 同一品物の複数レコードを「同じ key のバージョン列」として識別(正規化 `item_key` + `supersedes` ポインタ)
  - 検索時: ある品物にヒット → **その全バージョンをまとめて取得**(top-1 だけにしない) → LLM へ
  - prompt 断片 + 回答テンプレート(周が設計): 「複数の適用期間がある場合は時系列で説明し、片方だけを選ばない」
  - 「今」の判定: 現在日付 vs `effective_date` の比較
- **STAGE 02 に依存**: スキーマに日付項目; 検索層が「品物 key で全バージョンを返す」こと

### 4-3 早見表にない品物でも、類似品物の情報から案内する

- **場面**: 「モバイルバッテリー」を聞かれ早見表にない → 最も近いもの(「充電式電池」)を探す → 「類似する『充電式電池』に準じると XX として出す。ただし早見表に個別記載がないため、確実な分別は市に確認を」。
- **必要な仕組み**:
  - 早見表の全品名 + 説明を embedding し、小さいインデックスを作る(周が小型モデルを CPU で実行可能)
  - 構造化の「完全一致 / 部分一致」が両方 miss → 類似度検索を発火 → top-k 類似品物 + スコア
  - 回答には**「これは類推であり原文ではない」と明記**(安全側、STAGE 06 と整合)
- **STAGE 02 に依存**: 早見表の構造化データ(品名 + 説明があれば周がこの部分を作れる)、または STAGE 02 が作ったベクトルストアの再利用

## 4. STAGE 02/03 担当へのお願い(本田さん・藤井さん・FANG さん)

STAGE 04 は皆さんの検索層の**外側に被せる**形で作り、内部ロジックは変えない。
後で噛み合うよう、設計時に 4 点だけ確保してほしい。

### ① ナレッジレコードのスキーマ — 以下の項目を追加してほしい

各レコード(早見表の項目 / 説明ページの chunk / お知らせ)に、内容とは別に:

| 項目 | 型 | 説明 |
|---|---|---|
| `source_url` | str | 参照ページ URL(2-2 でも使用) |
| `source_type` | enum | `hayamihyo` / `shushubi` / `description` / `notice` |
| `fetched_at` | date | 取得日時 |
| `published_at` | date \| null | ページ上の更新日 / 公示日 |
| `effective_date` | date \| null | 適用開始日(基礎クロールデータは null = 常時有効) |
| `valid_until` | date \| null | 失効日 |
| `supersedes` | id \| null | このレコードが置き換える旧レコードへの参照 |
| `content_hash` | str | 差分用 |
| `item_key` | str | 品名の正規化キー(バージョン列 + 類似度用) |

### ② 検索ロジックを安定した関数として切り出してほしい

こういうシグネチャ(名前は相談可)。STAGE 04 はこれらを wrap し「バージョン統合 + 類似度フォールバック + 時系列」を足す:

- `lookup_item(name_or_key) → list[Record]` — **その品物の全バージョンを返す。top-1 だけにしない**
- `search_descriptions(query, k) → list[Chunk]`
- `list_knowledge_sources() → list[SourceMeta]` — WebUI 2-3 と STAGE 04 の manifest で共用

### ③ ナレッジファイルの物理配置と読み込み方法

- 基礎クロールデータをどのディレクトリに、どの形式で置くか
- 追加取込データを基礎データと**同一の**インデックスにどうマージするか
- 「インデックス再構築」のコマンド/関数はあるか — 周の ingest 後にそれを呼ぶ

### ④ 回答内の出典フォーマット

皆さんが「回答末尾に `出典: <URL>`」を定めると想定。STAGE 04 はそれを「複数出典 + 切替日」に拡張する。
今のうちに一緒に決めたい: 出典を SSE 本文に入れるか、別フィールドにするか、WebUI 表示のみにするか。

## 5. 中文サマリー(周・FANG 向け)

### STAGE 4 是什么

STAGE 2/3 假设知识静态,STAGE 4 处理"知识会变":

- **4-1 新知识导入即反映** — 建 ingest 动作(解析→同构记录→写库→重建索引)+ 知识源清单。依赖 STAGE 2 的 schema / 写入口 / 索引重建。
- **4-2 新旧并存不武断** — 每条记录带 `effective_date` / `published_at` / `valid_until`;同一品物按 `item_key` + `supersedes` 组成版本链;检索按品物 key 返回**全部版本**;LLM 用时间线话术,禁止只选一个。依赖 STAGE 2 的时间字段和"返回全版本"的检索。
- **4-3 早见表外品物类推** — 品名+说明 embedding,结构化 miss 后触发相似度,top-k 类似品物;回答必须标注"这是类推非原文"。依赖 STAGE 2 的早见表结构化数据或向量库。
