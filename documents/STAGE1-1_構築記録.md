## 2. 構成

```
採点サーバー ──POST /chat──> [ B1: 160.251.238.168:8000 ]
                                 │
                                 ├─ systemd: rag-chatbot.service
                                 └─ uvicorn (FastAPI, 自作)
                                      └─ vLLM AsyncLLMEngine (in-process)
                                           └─ Qwen3-VL-8B-Instruct (FP8量子化)
```

## 4. 詰まった点と原因(メンター説明用)

構築中に3回起動失敗しており、いずれも根本原因を特定して解消済み。

| # | 症状 | 根本原因 | 対処 |
|---|---|---|---|
| 1 | `Application startup failed`。Tritonのカーネルビルドで停止 | `fatal error: Python.h: No such file or directory` — TritonがCUDAユーティリティのC拡張を実行時JITビルドするのに、Pythonの開発ヘッダが未導入だった | `python3-dev` を導入 |
| 2 | systemdが5秒おきに再起動を繰り返し、毎回 `ValueError: Free memory on device cuda:0 (4.56/22.04 GiB) is less than desired GPU memory utilization` | 手動起動時のプロセスを親PIDだけ `kill` した結果、**vLLMの子プロセス `VLLM::EngineCore` が孤児として残り17.7GBのVRAMを保持し続けていた**。`nvidia-smi` のプロセス一覧にはGPUパススルーVMの都合で表示されず気づきにくい(`sudo fuser -v /dev/nvidia*` で特定) | 孤児プロセスをPID指定で終了。以後はsystemd管理とし、`systemctl stop` がcgroup単位で子プロセスごと回収することを実測確認(停止後VRAM 0 MiB) |
| 3 | `FileNotFoundError: [Errno 2] No such file or directory: 'ninja'` | FlashInfer(vLLMのサンプリングカーネル)が起動時にCUDAカーネルをJITビルドするのに `ninja` が必要 | `ninja-build`(apt)と `ninja`(venv内pip)を導入 |

## 5. 性能上の改善(自動採点対策)

### 起動時ウォームアップの追加
JIT/Tritonコンパイルは**初回リクエスト時に走る**ため、対策前は次の状態だった:

| リクエスト | 対策前(サービス再起動直後の1発目) | 対策後 |
|---|---|---|
| テキスト | TTFT **約13秒** | **0.047秒** |
| 画像 | TTFT **約12.3秒** | **0.132秒** |

採点サーバーの1発目がこのコストを踏むと速度評価が大きく劣化するため、起動処理の中でダミーのテキスト生成・画像生成を1回ずつ実行し、コンパイルコストを起動時に前倒しした。ポートのLISTENはウォームアップ完了後に開始されるため、**外部から接続できた時点で必ずウォーム状態**になる。

### processor の重複ロード解消
`AutoProcessor.from_pretrained()` が毎リクエストで呼ばれていたため、起動時に一度だけロードする形に修正。

### 起動時間
- 初回(コンパイルキャッシュなし): 約2分20秒
- 2回目以降(キャッシュ済み + ウォームアップ込み): **約61秒**

## 7. 既知のリスク(STAGE 2以降で対応)

### 7-1. 回答が冗長で、180秒制限を圧迫する【要対応】
「ペットボトルはどう捨てますか?」という単純な質問に対し **765トークン / 30.7秒**を要した(WebUI実測)。
複数ターンテストでも2ターン目が31.05秒。1ターン120秒・1問合計180秒の制限に対し、この長さのターンが
**3回続くと上限に達する**。速度評価の観点でも不利。

対策案:
- `max_tokens` を 1024 → 512 程度に抑制
- 「簡潔に、結論から答える」旨のsystem promptを導入(STAGE2で出典を本文に含める必要があるため、
  短くしすぎない匙加減が要る)

### 7-2. 回答内容は現状ほぼ誤り(RAG未実装のため)
「ペットボトルは『プラスチックごみ』に分類されます」等、北九州市の実際の分別と異なる回答をしている。
これは**STAGE 1の範囲外**(STAGE 2でRAGを実装して初めて正しくなる)であり、現時点では
「モデルが日本語で流暢にストリーミング応答できる」ことのみを確認したものと位置づける。

## 9. WebUI(2026-09-07 実装)

`http://160.251.238.168:8080/` — 課題p.43「WebUIを用意し、メンターがアクセスできる状態にしてください」に対応。

### 機能
- **チャット** — ストリーミング表示(逐次描画)、Markdown描画(見出し・箇条書き・強調・コード)
- **画像添付** — base64にして `img` に載せる。STAGE3-2の下地
- **VRAMリアルタイム表示**(STAGE1-3)— 1秒間隔でポーリング、使用量バー・GPU使用率
- **速度表示**(STAGE1-2)— 初回トークンまで / 生成完了まで / トークン数 / スループット
- **セッション管理** — セッションIDを表示、「新しい会話」で文脈をリセット。複数ターンの動作をその場で実演できる
- ダーク/ライトはOS設定に追従

### アクセス制御の設計

同じ8080番ポート上で、**採点用と人間用を経路レベルで分離**している。

| 経路 | 認証 | 到達範囲 |
|---|---|---|
| `POST /chat` | なし(採点サーバーは認証ヘッダを付けないため仕様上必須) | **アプリ側で送信元IPを検証**し、`160.251.239.96` 以外は403 |
| `POST /ui/chat` | パスワード(WebUI用。生成処理は `/chat` と同一) | 誰でも到達可・パスワード必須 |
| `GET /` `/vram` `/info` | パスワード | 同上 |

- パスワードは `/etc/rag-chatbot.env`(root所有・600)に置き、systemdの `EnvironmentFile` 経由で環境変数として渡す。**コードにもunitファイルにも平文を書いていない**
- ブラウザはログインフォーム+HttpOnly Cookie(24時間)。`curl -u` によるBasic認証も併用可(スクリプト検証用)
- 当初HTTP Basic認証のみだったが、`http://user:pass@host/` 形式のURLで開くとブラウザが
  「Request cannot be constructed from a URL that includes credentials」でfetchを禁止し、
  **画面は出るが監視パネルが無言で死ぬ**という罠があったため、ログインフォーム方式に変更した

### ブルートフォース対策の置き場所
当初 `ufw limit`(30秒に6接続)を使ったが、**チャット1通ごとにSSE接続が張られるため通常利用で誤爆する**
(実際に検証中、自分たちの接続が遮断された)。接続数ではなくログイン試行を制限すべきなので、
ファイアウォールは通常の `allow` に戻し、**アプリ側で「同一IPから5分間に8回失敗で429」**とした。

### 検証(外部ネットワークから、Cookieを持たない新規訪問者として)

| 手順 | 結果 |
|---|---|
| 未ログインで `/` を開く | 303 → `/login` |
| ログインページ表示 | 200 |
| 誤ったパスワード | 303 → `/login?e=1`(エラー表示) |
| 正しいパスワード | 303 + Cookie発行 |
| WebUI表示 | 200 |
| `/ui/chat` でストリーミング | 正常 |
| 同一session_idで2ターン目 | 文脈を維持 |
| Cookieを持っていても `/chat` | **403**(採点経路は非採点IPから叩けない) |

ブラウザ実機でもログイン→送信→逐次描画→監視パネル更新まで動作確認済み。
