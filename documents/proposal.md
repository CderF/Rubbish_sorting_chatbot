## 3. 確定要件(Known-knowns)

### 3-1. 対象範囲・チーム体制

- Teamb1〜4全員が使う**本番実装**として作る(個人検証ではない)。ドキュメント化・引き継ぎやすさを意識する
- データソースは指定URL `https://www.city.kitakyushu.lg.jp/kurashi/menu01_0391.html` に加え、**同ドメイン内の関連リンクを全てクロール**する(単一ページのみでは不十分と判断)

### 3-2. 実測したデータ構造

WebFetchで実ページを確認済み:

| ページ種別 | URL例 | 構造 |
|---|---|---|
| ハブページ | `menu01_0391.html` | ナビゲーションのみ、実内容なし |
| ごみの分別早見表 | `menu01_0393.html` → `/contents/924_10041.html` 等8ページ(あ行〜わ行) | **3カラムHTML表**(品名/出し方/備考)、推定300品目以上 |
| 資源とごみの収集日 | `menu01_0394.html` → 7区の個別ページ(例: `/contents/924_10102.html`) | 区内を**町名・丁目単位**(1区あたり100以上)で分割、ごみ種別(家庭ごみ/プラスチック/粗大ごみ等)ごとに収集曜日が異なる表形式データ |
| その他説明ページ | ごみステーション、指定ごみ袋、ごみ出し支援 等 | 通常の説明文・注意事項 |

### 3-3. アーキテクチャ方針(ハイブリッド構成)

1. **構造化データパス**(早見表・収集日カレンダー)
   - HTML表をパースし、JSON/SQLite等の構造化データとして保存
   - 品名検索は **DB完全一致 → 部分一致(LIKE) → ベクトル類似度** の段階的フォールバック(表記揺れ・俗称対応)
   - 収集日は「区 × 町名 × ごみ種別」をキーとした正確なルックアップ
2. **ベクトルRAGパス**(説明・注意事項ページ)
   - 通常のチャンク化 → embedding → 類似度検索
3. LLM(`Qwen3.5-9B`)は**意図解釈と自然文回答生成のみ**を担当し、事実情報は上記2パスの検索結果に基づいて生成する(ハルシネーション対策)

### 3-4. 使用ライブラリ・技術スタック

| レイヤー | 選定 | 備考 |
|---|---|---|
| RAG検索オーケストレーション | LangChain等の既存ライブラリ | 実装速度優先。**「高度なフレームワーク」該当性はメンター確認が必要**(下記「確認事項」参照) |
| Embeddingモデル | 軽量日本語対応モデル(例: `intfloat/multilingual-e5-small`、~118M param、VRAM数百MB) | LLMと同一L4 GPUに常駐させてもVRAM圧迫が小さい |
| ベクトルストア | **推奨: Chroma**(未確定、チーム判断待ち) | メタデータ(URL・更新日)フィルタが必要なSTAGE04(新旧情報並存)との相性を優先し推奨。FAISSも選択肢 |
| WebUI | Streamlit または Gradio | 実装速度優先。チャット画面 + VRAMモニター(STAGE1-1流用) + ナレッジ一覧表示(STAGE02-3要件)を実装 |
| データ取得 | 再実行可能なクローリングスクリプト | STAGE04の動的ナレッジ拡張を見越し、一回限りのスナップショットではなく差分更新できる構成にする |

### 3-5. STAGE02要件との対応

| 要件 | 対応方針 |
|---|---|
| 2-1 分別情報を根拠に回答 | ハイブリッド検索(構造化DB + ベクトルRAG)の結果をLLMが自然文化 |
| 2-2 根拠を参照ページまで示せる | 各チャンク・DBレコードに `source_url` メタデータを保持し、回答に引用として付与 |
| 2-3 検索対象の外部データファイル一覧と内容をWebUIで確認できる | WebUI(Streamlit/Gradio)に取り込み済みページ・ファイル一覧と内容ビューアを実装 |
