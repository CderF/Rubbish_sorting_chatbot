## 2. 要件ごとの実装方針

### 2.1 6-1 — 担当範囲外・確認不足の相談

> 他自治体やごみ以外の話題は担当範囲の外だと伝え、市が収集しない品物は収集しないことと正しい相談先を示し、
> いずれも推測で答えず、前提が足りない相談は決め打ちせず確認する

3つのサブケースに分解する:

**(a) 他自治体・ごみ以外の話題 → 担当範囲外を伝える**

検出方式は**ごみ語彙ホワイトリスト + 他都市名ブラックリストの2段判定**:

1. まずプロンプトに「ごみ・資源・分別・収集・捨て方」等のごみ関連語が**無ければ**即座に範囲外(天気・雑談・一般知識質問等を広く弾ける。個別の無関係トピックを網羅列挙する必要が無い)
2. ごみ関連語があっても、プロンプト中に北九州市**以外**の自治体名(例: 東京都・大阪市・福岡市・京都市 等、代表的な政令指定都市・県庁所在地を中心に初期リストを作る)が含まれていれば範囲外と判定する

初期ブラックリストは実装時に周と確定する(本文書では「代表的な都市名リストを用意する」という方針までを確定事項とする)。

⚠️ **既知の誤判定リスク**(確認済みの要注意点): 北九州市内の地名が他都市名と字面上重なる可能性がある
(例: 区名・町名の一部漢字が別都市の地名と一致するケース)。対策として:
- ブラックリストは完全一致または「都市名+行政区画語(都/道/府/県/市)」のセット一致を基本とし、単漢字の部分一致では発火させない
- `extract_region()`が北九州市内の区名(`WARDS`)・町名を検出済みの場合は、他都市名ブラックリストの判定より**後**に評価し、地区名が北九州市内のものと確定していれば誤検出を上書きで解除する
- 実装後、既存の`tests/collection_schedule_town_test.py`・`tests/notices_compound_name_test.py`等の実データ回帰(北九州市の実在地名)を全件流し、誤爆ゼロを確認してからマージする(4-3のときと同じ検証フロー)

**(b) 市が収集しない品物 → 収集しないことと正しい相談先**

既存の`disposal_method == "市が収集しないもの"`判定(§1参照)を土台に、備考(連絡先)がそのまま
案内されることを確認する。追加実装はほぼ不要 — 主眼は既存動作の回帰テスト追加。

**(c) 前提不足 → 推測せず確認する**

既存の`ans.missing.append("町名")`等のパターン(区名はあるが町名が無い場合に追記を促す)を踏襲。
新規に追加が必要なのは「品名すら特定できていないのに分別区分を聞かれている」ケース等の抜け漏れ確認。

**検出順序**: (a)を最優先(他の検索処理より前、`extract_region`の前段)。(b)(c)は既存の検索フローの中で
自然に扱われる。

### 2.2 6-2 — 危険・違法な処分の誘導への対応

> 危険・違法な処分を誘導する相談に乗らず、安全側の案内ができる

**スコープ**: ごみ処分そのものに関する違法・危険な処分方法の誘導のみを対象とする
(例: 野焼き・不法投棄・穴を開けずにスプレー缶を捨てる等、証拠隠滅目的の処分方法を尋ねる質問)。
ごみと無関係な一般的危険話題は対象外(§0)。

検出方式は6-1と同じ「代码側確定性ゲート + canned_response」。判定は
**危険処分の意図を示す動詞・表現**(例: 焼く/燃やす、埋める、川や山に捨てる、穴を開けずに、ばれないように
等)と**ごみ・処分の文脈語**の共起で発火させる(単語単体では発火させない — PIJ対策の`guard.py`が採る
「メタ語×操作語の共起」と同じ誤検知抑制の考え方。実装コードは流用しないが、設計思想は踏襲する)。

検知したら、該当品目が既存データにあればその正規の出し方を、無ければ一般的な「安全な処分方法を
北九州市の窓口に確認する」旨の固定文で案内し、危険な方法には一切触れない。

---

### 2.3 6-3 — 未知パターンでの安全側フォールバック

> 事前に想定していないパターンの相談でも、破綻せず安全側に対応できる

典型ケース: 6-1(範囲外)にも6-2(危険)にも該当せず、かつ品目検索・収集日検索のどちらにもヒットしない
「完全な空振り」。

**方針**: 既存の`_RULES_NO_CONTEXT`(プロンプト指示のみ)を、6-1/6-2と同じ**硬性canned_response**に
格上げする。`ans.found`が`False`かつ他のcanned_responseゲートも未発火の場合、検索結果ゼロを
LLMに渡して「見つかりませんでした」と言わせるのではなく、コード側で固定文
(「該当する情報が確認できませんでした。北九州市の公式ページまたは窓口(093-582-2201 環境局 等、
実際の窓口番号は実装時に確認)でご確認ください」)を返し、生成自体をスキップする。

これにより、STAGE02〜05で構築した「検索結果に無いことをLLMが自前の知識で埋めてしまう」リスク
(4-3で繰り返し確認された既知の失敗モード)を、未知の入力パターンに対しても一貫して防げる。

---

### 2.4 6-4 — 判断過程の事後確認可能性

> どう調べて・どう判断してその回答に至ったかを、後から確認できる

**受け手**: メンター(自動採点合格後にWebUIで確認する運用のため)。

**方針**: 既存の`build_trace_record()` / `var/stage4_trace.jsonl`を土台に、**新規WebUIページ**を追加する。
既存の`/knowledge`ページ(STAGE02 2-3、ナレッジソース一覧)と同じ認証(`require_login`)・同じ設計思想
(取り込み済みデータをメンターがブラウザで確認できる)を踏襲する。

表示内容の初期案(実装時に精査):
- セッション/リクエスト単位で、検出した地区・品目・マッチ段階(exact/partial/vector/analogy)
- 採用した根拠URL(`sources`)
- 発火したcanned_responseゲート(6-1/6-2/6-3のどれが発火したか、あるいは未発火)
- 4-2(時系列)・4-3(類推)等、既存のトレース項目も引き続き表示

⚠️ 既存WebUI同様、**必ず`require_login`で保護する**(生のプロンプト履歴が含まれるため、未認証公開は避ける)。

## 3. 画像分類パス(STAGE03 3-2)への適用

ユーザーが画像を渡すケース(`image_item_name`経由)にも6-1(a)(b)(c)・6-2のゲートを適用する必要があるか、
既存コードを確認した:

- `_blocking_route`は`image_item_name`が渡された場合、テキスト抽出をスキップして直接品名候補として扱う
  ([app/rag/router.py:591-617](../app/rag/router.py))
- 画像自体から「危険物を捨てたい」という**意図**(6-2)を読み取ることは、現行の画像分類パス
  (品目名相当の中間出力を生成するだけの設計、[[CONTEXT.md]]の「画像分類パス」定義参照)の範囲外
- 一方、画像に添付される**テキストプロンプト**(`prompt`引数、画像と同時に送られる文言)には
  6-1/6-2のゲートが通常通り適用される(ゲートはプロンプト文字列を見るのであって、画像分類の有無に
  依存しない)

**結論**: ゲート自体は`_blocking_route`の入口(`image_item_name`分岐より前)に置くため、画像添付の有無に
関わらず自動的に適用される。追加の分岐は不要。ただし「画像そのものが危険物の視覚的誘導になっている」
ケース(テキストには何も無いが画像だけで違法処分を示唆する等)は、現行のVLM構成では検出できない
既知の限界として明記し、対応は見送る(スコープ外)。

## 4. ゲートの実行順序とcanned_responseの優先順位

`_blocking_route`内の既存canned_responseは複数あり(4-3の`_ANALOGY_UNRELIABLE_REPLY`等)、
新規ゲートとの優先順位を明確にする:

```
1. 6-1(a) 範囲外判定        ← 最優先。検索処理(extract_region等)より前
2. 6-2    危険処分誘導判定  ← 6-1の直後。検索処理より前
3. (通常の検索フロー: extract_region → item検索 → schedule検索 → 4-2/4-3判定)
4. 6-1(b)(c) 市非収集・前提不足 ← 既存の検索フロー内で自然に扱う(追加ゲート不要)
5. 6-3    完全空振りフォールバック ← 検索フロー完了後、ans.found=False かつ他のcanned_response未発火のとき
```

理由: 6-1(a)/6-2は「そもそも検索する意味が無い(あるいは検索させてはいけない)」質問なので、
早見表検索・収集日検索のどちらも実行せずに即座に固定文を返す。4-2(時系列)・4-3(類推)のcanned_response
は検索結果に応じて検索フローの後半で確定するため、6-1(a)/6-2より後になる。6-3は「他の全ゲートを
くぐり抜けて、かつ何もヒットしなかった」最終フォールバックとして最後に置く。
