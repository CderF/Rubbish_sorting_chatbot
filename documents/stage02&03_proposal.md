## 3. 確定要件(Known-knowns)

### 3-1. 対象範囲・チーム体制

- Teamb1〜4全員が使う**本番実装**として作る(個人検証ではない)。ドキュメント化・引き継ぎやすさを意識する
- データソースは指定URL `https://www.city.kitakyushu.lg.jp/kurashi/menu01_0391.html` に加え、**同ドメイン内の関連リンクを全てクロール**する(単一ページのみでは不十分と判断)

### 3-2. 実測したデータ構造

WebFetchで実ページを確認済み:

| ページ種別 | URL例 | 構造 |
|---|---|---|
| ハブページ | `menu01_0391.html` | ナビゲーションのみ、実内容なし |
| ごみの分別早見表 | `menu01_0393.html` → `/contents/924_10041.html` 等8ページ(あ行〜わ行) | **3カラムHTML表**(品名/出し方/備考)、推定300品目以上 |
| 資源とごみの収集日 | `menu01_0394.html` → 7区の個別ページ(例: `/contents/924_10102.html`) | 区内を**町名・丁目単位**(1区あたり100以上)で分割、ごみ種別(家庭ごみ/プラスチック/粗大ごみ等)ごとに収集曜日が異なる表形式データ |
| その他説明ページ | ごみステーション、指定ごみ袋、ごみ出し支援 等 | 通常の説明文・注意事項 |

### 3-3. アーキテクチャ方針(ハイブリッド構成)

1. **構造化データパス**(早見表・収集日カレンダー)
   - **早見表パス**: HTML表をパースし、JSON/SQLite等の構造化データとして保存。品名検索は **DB完全一致 → 部分一致(LIKE) → ベクトル類似度** の段階的フォールバック(表記揺れ・俗称対応)
   - **収集日パス**: 「区 × 町名 × ごみ種別」をキーとした正確なルックアップ。**地区は町名レベルまで必須**(区のみでは一意に定まらないため)。区のみ指定された場合は、推測で答えず町名の追加入力を促す(STAGE03 3-1対応)
2. **ベクトルRAGパス**(説明・注意事項ページ)
   - 通常のチャンク化 → embedding → 類似度検索
3. **画像分類パス**(STAGE03 3-2 新設)
   - VLM(`Qwen3-VL-8B-Instruct`)が渡された画像から品目名・特徴語を抽出し、以降は早見表パスに同じキーで問い合わせる
   - 画像入力であっても「品名相当の中間出力」を経由させることで、STAGE02 2-2の「回答の根拠を参照ページまで示せる」要件をSTAGE03でも一貫して満たす
4. LLM(`Qwen3-VL-8B-Instruct`)は**意図解釈と自然文回答生成のみ**を担当し、事実情報は上記各パスの検索結果に基づいて生成する(ハルシネーション対策)

### 3-4. 使用ライブラリ・技術スタック

| レイヤー | 選定 | 備考 |
|---|---|---|
| RAG検索オーケストレーション | LangChain等の既存ライブラリ | メンター確認済み、使用可 |
| Embeddingモデル | 軽量日本語対応モデル(`intfloat/multilingual-e5-small`、~118M param、VRAM数百MB) | LLMと同一L4 GPUに常駐させてもVRAM圧迫が小さい |
| ベクトルストア | **Chromaに確定** | メタデータ(URL・更新日)フィルタが必要なSTAGE04(新旧情報並存)との相性を優先 |
| WebUI | Streamlit または Gradio | チャット画面 + VRAMモニター(STAGE1-1流用) + ナレッジ一覧表示(STAGE02-3要件) + **画像アップロード入力(STAGE03 3-2対応、新規)** |
| データ取得 | 再実行可能なクローリングスクリプト | STAGE04の動的ナレッジ拡張を見越し、一回限りのスナップショットではなく差分更新できる構成にする |

### 3-5. STAGE02要件との対応

| 要件 | 対応方針 |
|---|---|
| 2-0 自然言語で検索可能なDBを構築する | 早見表パス・収集日パスを構造化DB化、説明ページをベクトルDB化 |
| 2-1 分別情報を根拠に回答 | ハイブリッド検索(構造化DB + ベクトルRAG)の結果をLLMが自然文化 |
| 2-2 根拠を参照ページまで示せる | 各チャンク・DBレコードに `source_url` メタデータを保持し、回答に引用として付与 |
| 2-3 検索対象の外部データファイル一覧と内容をWebUIで確認できる | WebUI(Streamlit/Gradio)に取り込み済みページ・ファイル一覧と内容ビューアを実装 |

### 3-6. STAGE03要件との対応

| 要件 | 対応方針 |
|---|---|
| 3-1 品名と地区を伝えると、出し方と収集日まで案内できる | 単一リクエスト内で品名+町名レベルの地区が揃っていることを前提に、早見表パス(出し方)と収集日パス(区×町名×ごみ種別)を並行検索し統合して回答。片方でも情報が不足する場合は推測せず、不足項目を明示して再入力を促す(マルチターンでの補完はSTAGE05のスコープとし本段階では非対応) |
| 3-2 品名の代わりに品物の画像を渡しても、分別を判定して案内できる | VLM(`Qwen3-VL-8B-Instruct`)が画像から品目名を抽出し、以降は3-1と同じ早見表パスに合流。WebUIに画像アップロード入力を追加し、メンターがUI上で画像テストできる状態にする |

### 3-7. 未識別・未検出時の基本方針

STAGE06(安全対応)自体は本提案の対象外だが、STAGE03の実装では「該当なし」のケースに必ず遭遇するため、最低限の原則をここで定める:

- 早見表に該当品目が見つからない場合: 「該当情報が見つからない」旨を明示し、憶測で分別区分を断定しない
- 画像から品目を特定できない場合: 「画像から品目を特定できませんでした」と伝え、テキストでの品名入力を促す
- 指定された町名が収集日データに存在しない場合: 「該当地区データが見つからない」旨を伝え、区名・町名の再確認を促す
- 上記いずれも、評価軸の「回答精度」においてハルシネーションを避けることを優先する

- **STAGE04(動的ナレッジ拡張)**: 再実行可能なクローリングスクリプトという土台のみ維持(旧提案から継続)。新旧情報のバージョン管理ロジックの詳細設計は行わない
