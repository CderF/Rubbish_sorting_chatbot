## 3. Apache 2.0 ライセンスの要点(Qwen2.5 に適用)

- 商用利用・改変・非公開デプロイ・再配布すべて許可
- 著作権表示と NOTICE ファイル(付属していれば)の保持義務のみ。派生物を再度オープンソース化する義務(コピーレフト)はない
- 利用者数上限や禁止用途リストのような制約条項が存在しない(Llama 3.1 / Gemma とはここが異なる)
- → 「L4サーバーでセルフホストし社内で使う」という今回の要件と非常に相性が良い

## 4. 禁止ツールに抵触しないか

課題資料 p.43:
> Dify・Agent SDK・Ollama等、高度なフレームワークの利用禁止

- Qwen2.5 はモデルの重みそのものであり、フレームワークではないため本条項の対象外
- 推論エンジンとして **vLLM**(Apache 2.0)を検討中。Dify / Agent SDK / Ollama のいずれでもないが、内部でスケジューリングやバッチ処理を自動化する「比較的高度なフレームワーク」でもある。
  → **この点はメンターに直接確認が必要**(下記「確認事項」参照)
  - 禁止と判断された場合: `transformers` + `TextIteratorStreamer` + 自作 FastAPI による、より低レベルで完全に説明可能な構成に切り替える(スループットは vLLM より劣るが、原理を全て自分たちで説明できる)
  - 許可された場合: vLLM の `AsyncLLMEngine` を自作 FastAPI の `/chat` ルート内から呼び出す形にする。内部処理(PagedAttention・continuous batching)は仕組みとして説明可能
- いずれの構成でも、外部(採点サーバー)に公開するのは自分たちで実装した `/chat` エンドポイントのみで、Dify/Ollama のような「ブラックボックスな一発デプロイ」にはならない → 「AIでの開発推奨(ただし説明できるように)」の要件を満たせる

## 6. 想定する構築手順(STAGE 1-1で実施予定、ここでは実現可能性の裏付けとして記載)

> **✅ 2026-09-07 実施済み**: 下記1.のドライバ+CUDA導入は両サーバーで完了。B1(168)・B2(57)ともに `nvidia-driver-595-server`(595.71.05, LTSに近い成熟ブランチを選定)+ `cuda-toolkit`(13.3.1)を NVIDIA公式apt リポジトリ(`cuda-keyring`経由)から導入し、reboot後 `nvidia-smi` で **NVIDIA L4 / 23034MiB** を両機とも確認済み。B2は途中でカーネルイメージが `5.15.0-190→191` に更新されたため、両カーネル分の `linux-headers` を導入してからDKMSビルド・rebootし、`uname -r` が `191` になったことも確認済み。`nvcc --version` も両機で正常動作(13.3.73)。

1. NVIDIA ドライバ導入(Ada Lovelace/L4 は driver ≥ 525 が必要、535/550系のデータセンター向けドライバを推奨)+ CUDA 12.x
2. `python3 -m venv` で仮想環境作成、`pip install vllm`(対応する torch も併せて入る)
3. `huggingface-cli download Qwen/Qwen2.5-7B-Instruct` で重みを取得(~15GB、空き容量86GBに対し余裕あり)
4. 自作 FastAPI サーバーを起動し、内部で vLLM の `AsyncLLMEngine`(または transformers streaming)を呼び出して、課題指定の
   - `POST /chat`、body `{session_id, prompt, img}`
   - `Content-Type: text/event-stream`、`data: {"delta": "..."}\n\n` 形式の逐次配信
   を実装する
5. `nvidia-smi --query-gpu=memory.used,memory.total --format=csv -l 1`(または `pynvml`)をポーリングする簡易 WebUI を用意し、VRAM使用量をリアルタイム表示(STAGE1-3要件)
6. FastAPI内で `time.perf_counter()` により生成開始〜終了の所要時間を計測・記録(STAGE1-2要件)

## 9. 追記(2026-09-07)— サーバー1台限定・画像対応必須という制約への対応

### 9-1. なぜ最初の調査でQwen3を検討しなかったか(率直な経緯)

初稿では Qwen2.5 系列を「実績があり安全な基準」として調査したが、**Qwen3系列の存在を確認しないまま除外していた**。意図的に避けたわけではなく単純な調査漏れ。改めて Hugging Face 公式ページを WebFetch で確認したところ:

- Qwen3(テキスト専用)、Qwen3-VL(視覚言語統合)シリーズがともにリリース済み
- いずれも Qwen2.5 と同じ **Apache License 2.0**(ライセンス面での懸念は生じない)
- 推論エンジン vLLM は 2026-08-26 リリースの最新版 `0.28.0` が Qwen3-VL(要件は ≥0.11.0)に既に対応済みで、`pip install vllm` するだけで自動的に満たされる

→ ライセンス・ツール対応いずれも問題なし。**除外していた理由は「調査不足」であり、技術的な忌避理由ではなかった**ため、以下の通り採用候補に追加する。

### 9-2. サーバー1台+画像対応という制約への回答

テキスト専用モデルと画像分類用モデルを別々に2つロードする構成は、GPU 1枚(24GB)しかない前提では非現実的(2モデル同時ロードでVRAM不足が確実)。そのため **Vision-Language(VL)モデル1つでテキストQAと画像入力の両方を処理する**方針に変更する。

候補比較(すべて WebFetch で公式情報を直接確認):

| モデル | パラメータ | License | vLLM対応 | 特徴 | BF16重み概算 | 単一L4(24GB)での見立て |
|---|---|---|---|---|---|---|
| **Qwen3-VL-8B-Instruct** | 9B | Apache 2.0 | vLLM ≥0.11.0(最新0.28.0で確実に対応) | OCR 32言語対応、Qwen3世代のテキスト性能を継承、ネイティブ256Kコンテキスト、Interleaved-MRoPE/DeepStack等の新アーキ | 約18GB | 重みだけで18GB、残り約4〜6GBがKVキャッシュ用とやや窮屈。**vLLMのFP8オンザフライ量子化**(Ada Lovelace/L4はFP8 Tensor Core搭載でネイティブ対応)で重みを~9GBまで圧縮すれば大幅に余裕ができる |
| Qwen2.5-VL-7B-Instruct | 約8.3B | Apache 2.0 | 対応済み・実績豊富 | 公式AWQ量子化版あり、コミュニティ事例が多く枯れている | 約16〜17GB | 重み16〜17GB、残り7〜8GB。量子化なしでも比較的安全に単カード運用可能 |

**最終方針**: 精度を優先して **Qwen3-VL-8B-Instruct(FP8量子化前提)** を第一候補とする。VRAM逼迫や、リリースから日が浅いことによるvLLM/エコシステム側の未知の不具合が実機検証で出た場合は、実績豊富な **Qwen2.5-VL-7B-Instruct**(公式AWQ量子化版あり)に切り替える、という段階的な方針とする。どちらも Apache 2.0 でライセンス・禁止ツールの懸念はなく、1台のL4サーバー・1モデルでテキストQA(STAGE1-2)と画像による分別判定(STAGE3-2)の両方を満たせる構成になる。

## 10. 追記2(2026-09-07)— なぜ最新の Qwen3.8 系列を使わないか

Qwen は 2026年8月に **Qwen3.8** 系列(フラッグシップ刷新)をリリース済み。WebFetch で Hugging Face を直接確認したところ、以下の構成であることが判明:

| モデル | 総パラメータ | 構造 | 画像対応 | 公式量子化 |
|---|---|---|---|---|
| Qwen3.8-27B | 27B(実質28B表記) | 非MoE、Gated DeltaNet + Gated Attentionのハイブリッド構造、**ネイティブ視覚言語対応**(画像・動画理解) | ○ | FP8版のみ公式提供 |
| Qwen3.8-Flash-Next | 180B | MoE | ○ | FP8版のみ公式提供 |
| Qwen3.8-2.4T-A95B | 2.4T(A95B=活性化95B) | 超大規模MoE | — | FP8版のみ公式提供 |

ライセンスは Qwen3系と同じ **Apache 2.0** で問題なし。vLLM も対応済み。ただし**単一L4(24GB)に載るサイズが存在しない**という決定的な問題がある:

- 最小モデルの Qwen3.8-27B でも **BF16で重みだけ約54GB**
- 公式提供の量子化は **FP8のみ**で、それでも **重み約27GB** となり、24GB全部を重みだけで使い切ってもまだ足りない(KVキャッシュ・CUDAオーバーヘッドの余地が一切ない)
- 24GBに収めるには **INT4級の量子化が必須**だが、Qwen公式はINT4版を提供しておらず、コミュニティ製の非公式量子化(GGUF/NVFP4など)に頼るしかない。しかも Qwen3.8 は **2026年8月リリースでまだ1ヶ月程度**しか経っておらず、量子化・vLLM対応いずれも枯れておらず、精度劣化やバグのリスクが高い

**結論**: Qwen3.8 は「最新だから」という理由だけでは採用しない。ライセンスやフレームワーク対応の問題ではなく、**純粋にハードウェア制約(単一24GB GPU)に収まらない**ことが不採用の理由。段階5(Qwen3.8-27Bの3.8世代)は次サイクルでチームがサーバー増強・複数GPU構成に移行できるタイミングがあれば改めて検討する価値がある。今回は「単一L4に収まり、Apache 2.0で、画像対応もある」条件を満たす **Qwen3-VL-8B-Instruct**(9. 節参照)を採用する。
